# Issue tracker: GitHub

Issues and PRDs for this repo live as GitHub issues. Use the `gh` CLI for all operations.

## Conventions

- **Create an issue**: `gh issue create --title "..." --body "..."`.
- **Read an issue**: `gh issue view <number> --comments`, also fetching labels.
- **List issues**: `gh issue list --state open --json number,title,body,labels,comments` with appropriate label and state filters.
- **Comment on an issue**: `gh issue comment <number> --body "..."`
- **Apply or remove labels**: `gh issue edit <number> --add-label "..."` or `--remove-label "..."`
- **Close an issue**: `gh issue close <number> --comment "..."`

## Root-cause issue contract

- Create one issue per confirmed root cause, not one issue per bot comment.
- Put links to every duplicate CodeRabbit, Codex, Cursor, or other automated
  finding on the same root-cause issue.
- The durable Agent Brief is the implementation contract. It records current
  and desired behavior, key interfaces, acceptance criteria, and explicit
  exclusions. Discussion and bot output remain supporting context.
- The issue is the only mutable task record. Do not mirror its state in
  `progress.md` or another ledger. Automated-review remediation does not use an
  umbrella issue.
- Every issue body or comment created during triage starts with
  `> *This was generated by AI during triage.*`.
- Keep the issue open at `artifact_verified`; close it only after
  `remote_verified` as defined in `docs/agents/production-flow.md`.

An automated-review comment on a PR may become evidence for a root-cause issue,
but the PR itself does not enter the triage-label state machine.

## Authorization

Once the user has approved the task boundary, Codex may create, edit, label,
comment on, and close its root-cause issues without separate confirmation for
each operation. Codex may also make a scoped local commit after
`artifact_verified`.

For a purely technical finding inside that approved boundary, this standing
delegation is the maintainer direction required after `/triage` states its
recommended category, state, and evidence. Wait for the user instead if the
decision changes product or UX behavior, expands scope, encounters conflicting
state labels, or needs an unusual state override.

Obtain the user's explicit authorization in the current turn before any push,
PR creation or update, merge, or comment that summons or reruns an external
review bot. Bot availability or quota failures must be reported; they are not a
passing review result.

Infer the repository from `git remote -v`; `gh` does this automatically when run inside the checkout.

## Pull requests as a triage surface

**PRs as a request surface: no.**

When changed to `yes`, external pull requests run through the same labels and states as issues. Read them with `gh pr view` and `gh pr diff`, and manage them with the corresponding `gh pr` commands.

GitHub shares one number space across issues and pull requests. Resolve a bare issue number with `gh pr view <number>` and fall back to `gh issue view <number>`.

## When a skill says "publish to the issue tracker"

Create a GitHub issue.

## When a skill says "fetch the relevant ticket"

Run `gh issue view <number> --comments`.

## Wayfinding operations

The `/wayfinder` map is one issue with child issues as decision tickets.

- **Map**: label it `wayfinder:map`.
- **Child ticket**: link it as a GitHub sub-issue. If sub-issues are unavailable, link it from a task list and add `Part of #<map>` to the child.
- **Blocking**: use GitHub native issue dependencies. If unavailable, add `Blocked by: #<number>` to the child.
- **Frontier**: select the first open, unassigned child with no open blockers.
- **Claim**: assign the issue to the active developer.
- **Resolve**: record the answer in a comment, close the child, and update the map's decisions.
