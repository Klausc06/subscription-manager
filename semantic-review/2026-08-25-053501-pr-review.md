# Dynamic Type / contrast fixes and file extraction refactors

Three commits bundled: a behavioral accessibility fix (44e9a8e addressing #95 and #112) and two structural refactors (53e4923 splitting LibraryView/WorkspaceSupport, e599878 splitting SwiftDataSubscriptionRepository). The a11y commit replaces fixed badge constraints with intrinsic-content sizing, scales the calendar height by Dynamic Type size category, swaps hardcoded colors for semantic tokens, and lets amount/date text wrap instead of compressing. The refactors are pure file extractions with no logic changes, promoting a handful of `private` free functions to `internal` so they can be shared across files.

Watch for: Badge UILabel lacks horizontal padding (confirmed) — at larger Dynamic Type sizes or with "99+" text the characters touch the background edge, degrading the legibility this commit aims to fix. The `calendarHeight` switch doesn't cover the full range between default and `.isAccessibilitySize` (likely gap at accessibility1–5 sizes).

**Verdict**: NEEDS_CHANGES

## High-level view

The badge sizing change moves from fixed 24×18pt constraints to intrinsic-content sizing with `adjustsFontForContentSizeCategory`, but omits content insets. A `UILabel` intrinsic size is the text bounding box alone, so the 9pt corner radius clips into the glyph area when text grows. Adding horizontal content insets would complete the fix.

The calendar height stepper covers `.xLarge` through `.xxxLarge` but the `default` case also catches accessibility sizes 1–5 (where the calendar is hidden by `showCalendar`). Functionally harmless today, but the switch doesn't guard its domain — if the hiding gate is later removed, the calendar renders at 360pt for sizes that need much more.

The UpcomingTimelineRow changes — removing `fixedSize(horizontal:)` and `minimumScaleFactor`, switching to `lineLimit(2)` — directly address the #112 spec requirement (no truncation of amount/date at XXXL).

The CatalogAlphabetIndex swaps `Color.white` → `.background` and `Color.accentColor` → `.tint`, adapting to light/dark mode and any accent color. Touch target widens from 28pt to 44pt (HIG minimum). This satisfies #95's legibility criterion for the alphabet index.

The `private` → `internal` access promotion for canonicalization helpers in the persistence refactor is the minimum change needed for multi-file visibility and introduces no new surface area outside the app target.

## Badge intrinsic sizing without content insets

The old badge used fixed 24×18pt constraints, which gave implicit whitespace around the text. The new layout:

```swift
badge.adjustsFontForContentSizeCategory = true
badge.widthAnchor.constraint(greaterThanOrEqualTo: badge.heightAnchor).isActive = true
badge.heightAnchor.constraint(greaterThanOrEqualToConstant: 18).isActive = true
badge.setContentHuggingPriority(.required, for: .horizontal)
badge.setContentCompressionResistancePriority(.required, for: .horizontal)
```

`UILabel.intrinsicContentSize` returns the tight bounding box of the rendered text. With no content insets, the colored background (9pt corner radius) eats into the visible glyph area once the text is wider than about 14pt — which happens at `.xLarge` Dynamic Type with "99+". The `cornerRadius` is also fixed at 9pt while the badge now grows; at larger sizes the radius should either scale or use `cornerRadius = bounds.height / 2` in `layoutSubviews`. [confirmed: lines 670–699 of UpcomingView.swift]

This partially undermines #95's acceptance criterion: "Badge and index remain legible with any accent color in light and dark mode." The color contrast is resolved, but physical legibility of the badge text at larger sizes is not guaranteed without insets.

## Calendar height scaling vs accessibility size domain

```swift
private var calendarHeight: CGFloat {
    switch dynamicTypeSize {
    case .xxxLarge: 420
    case .xxLarge:  400
    case .xLarge:   380
    default:        360
    }
}
```

The calendar is hidden entirely when `dynamicTypeSize.isAccessibilitySize` (checked via `showCalendar`). So `.accessibility1` through `.accessibility5` hit the `default` branch returning 360, but the calendar is never rendered. If someone later removes the hiding gate, the calendar will render at 360pt for accessibility sizes that need much more height. [likely: maintainability concern, not a runtime bug today]
